Préparation stratégique d’un projet NSI

Synthèse provisoire destinée à préparer le choix, l’architecture, la présentation et le déploiement d’un futur projet pour les Trophées NSI, avec comme contexte le Lycée Les Eucalyptus à Nice.

01 / Contexte

Trophées NSI

Le projet doit être pensé comme un projet informatique réel, mais rester clairement lié aux connaissances et compétences attendues dans la spécialité NSI.

Point central : un bon projet ne doit pas uniquement avoir une interface agréable. Le jury doit pouvoir identifier une véritable contribution algorithmique, technique et personnelle des élèves.

Objectif de conception

Créer un projet dont l’utilité est immédiatement compréhensible, dont le fonctionnement est facile à reproduire, et dont le code révèle une vraie profondeur informatique.

02 / Technologies

Stack de référence

À privilégier
  • Python 3
  • SQL
  • SQLite
  • Shell / scripts simples
  • Tkinter si interface desktop
  • HTML / CSS en complément
  • JavaScript client si réellement nécessaire
À éviter ou limiter
  • Dépendances très lourdes
  • Serveurs externes obligatoires
  • Docker comme prérequis
  • GPU obligatoire
  • Modèles IA locaux volumineux
  • Matériel spécifique
  • Dépendance au réseau interne du lycée

Principe architectural

PROBLÈME
   ↓
DONNÉES
   ↓
STRUCTURE DE DONNÉES
   ↓
ALGORITHME DÉVELOPPÉ PAR L'ÉQUIPE
   ↓
RÉSULTAT
   ↓
INTERFACE UTILISATEUR

Les bibliothèques doivent servir le projet, mais elles ne doivent pas devenir le projet lui-même.

04 / Persona

Archétype de jury

L’objectif n’est pas de deviner une personne précise mais de construire une persona suffisamment réaliste pour guider les décisions de conception.

Persona de référence

Évaluateur techniquement compétent, avec peu de temps disponible

Professeur de NSI, enseignant du supérieur, développeur, ingénieur informatique, chercheur ou étudiant avancé en informatique.

Il sait lire du Python, comprend les algorithmes et les structures de données et peut rapidement distinguer un vrai travail algorithmique d’une simple intégration de bibliothèques.

Questions probables dans son esprit

  • Quel problème ce projet résout-il ?
  • Pourquoi est-il utile ?
  • Qu’est-ce qui a réellement été développé par les élèves ?
  • Où est l’algorithmique ?
  • Pourquoi cette structure de données ?
  • Pourquoi cette bibliothèque ?
  • Le projet fonctionne-t-il vraiment ?
  • Puis-je le reproduire facilement ?
  • Les élèves comprennent-ils leurs propres choix ?
05 / Frictions

Douleurs possibles du jury

01

Démarrage difficile

Dépendances cassées, chemins absolus, clés API, configuration manuelle ou erreurs dès le premier lancement.

02

Projet difficile à comprendre

L’objectif, l’utilisateur ou la valeur du projet ne sont pas évidents dans les premières minutes.

03

Peu de travail propre

La partie impressionnante est essentiellement fournie par une API, un framework ou une bibliothèque externe.

04

Complexité artificielle

Trop de technologies ou d’architecture pour une tâche qui pourrait être résolue beaucoup plus simplement.

05

Autonomie douteuse

Difficulté à déterminer ce qui a été réellement développé par les élèves, notamment en cas d’utilisation importante d’IA générative.

06

Expérience non reproductible

Besoin d’un matériel, d’un compte, d’un serveur ou d’un réseau que le jury ne possède pas.

06 / Distribution

Expérience de lancement

L’objectif est de réduire le nombre d’étapes nécessaires avant que le jury puisse voir le projet fonctionner.

Niveaux possibles

Niveau Méthode Rôle
1 python main.py Chemin principal et reproductible
2 RUN_PROJECT.bat Réduction de la friction sur Windows
3 Version portable .exe Option pratique supplémentaire, jamais le seul moyen d’évaluer le projet
4 Installateur complet Seulement si réellement nécessaire
Attention aux exécutables Un fichier .exe non signé peut déclencher Windows SmartScreen ou un antivirus. Il ne doit donc pas être l’unique méthode permettant d’évaluer le projet. 
git clone ...
pip install -r requirements.txt
python main.py

Ce chemin doit rester simple, documenté et fiable.

06B / Vérification par le jury

Comment le projet sera vérifié

Le projet doit pouvoir être évalué de manière autonome par le jury, dans un environnement distinct de celui du lycée. L’objectif principal est la reproductibilité : le jury doit pouvoir comprendre, lancer, tester et inspecter le projet sans dépendre de la machine des auteurs.

Éléments disponibles pour l’évaluation

  • Vidéo de démonstration.
  • presentation.md.
  • Code source.
  • README.md.
  • requirements.txt.
  • Données ou exemples nécessaires à la démonstration.
  • Documentation technique éventuelle.

Scénario de vérification attendu

Comprendre le projet
Installer les dépendances
Lancer
Tester un exemple
Vérifier le résultat
Lire le code
Consulter la documentation

Le lancement doit fonctionner simplement

pip install -r requirements.txt
python main.py

Aucune modification manuelle du code, aucun chemin absolu et aucune configuration locale spécifique au Lycée Les Eucalyptus ne doivent être nécessaires.

Points susceptibles d’être vérifiés

Point Attente
Dépendances Installation complète depuis requirements.txt.
Démarrage Le projet démarre sans modification manuelle.
Données Un jeu de données de démonstration est disponible localement.
Internet La fonctionnalité principale reste testable hors ligne.
Permissions Pas de droits administrateur nécessaires.
Code La partie développée par les élèves est identifiable et lisible.
Algorithmes Les choix algorithmiques et les structures de données sont visibles.
Reproductibilité Le scénario présenté dans la vidéo peut être reproduit.

Erreurs à éviter pendant la vérification

ModuleNotFoundError
FileNotFoundError
API key missing
Permission denied
Connexion au serveur impossible
Chemin local introuvable
Version Python incompatible

Le projet doit afficher des messages compréhensibles lorsque l’environnement n’est pas correct, plutôt qu’un traceback brut.

Test interne avant remise

  • Tester depuis une copie propre du dépôt.
  • Installer uniquement avec requirements.txt.
  • Lancer avec python main.py.
  • Tester sans IDE.
  • Tester sans droits administrateur.
  • Tester sans connexion Internet.
  • Tester le scénario de démonstration complet.
  • Redémarrer le projet après fermeture.
  • Tester sur la machine Lenovo-1700 du lycée.
  • Vérifier la consommation mémoire.
Principe important La machine Lenovo-1700 sert de référence basse de compatibilité. Elle n’est pas la machine du jury et le projet ne doit dépendre ni de son réseau, ni de sa configuration locale.

08 / Références

Ce que montrent certains projets précédents

Les projets précédents ne permettent pas de déduire automatiquement les goûts personnels du jury. Ils servent cependant à identifier certains schémas intéressants.

PyCraft

Idée immédiatement reconnaissable combinée à une réalisation technique importante : environnement de type Minecraft, génération, affichage et logique propres.

Linux.pyxel

Simulation d’un environnement inspiré de Linux avec plusieurs commandes et outils développés dans le projet.

TaM Desktop

Projet lié à un besoin réel de transport, avec une dimension algorithmique de recherche d’itinéraire.

WheelShare

Plateforme de covoiturage scolaire ayant effectivement participé au concours mais n’ayant pas été sélectionnée. La raison exacte n’est pas publique.

Hypothèse WheelShare

L’une des hypothèses à étudier est qu’un projet de plateforme classique peut être utile sans montrer suffisamment vite une profondeur algorithmique ou une originalité informatique.

Important Cette explication n’est pas une justification officielle du jury. Elle doit rester clairement identifiée comme hypothèse.
09 / Recherche future

Hypothèses à vérifier

Confirmé

Informations issues des règles, documents officiels ou déclarations directes des participants.

Hypothèse

Interprétations utiles pour guider le projet, mais qui doivent encore être confrontées à plusieurs cas réels.

À vérifier

Informations manquantes ou trop incertaines pour être utilisées comme base de décision.

  • Les projets de type CRUD, chatbot ou simple wrapper d’API seraient-ils perçus comme moins intéressants ?
  • Une algorithmique clairement visible améliore-t-elle significativement les résultats ?
  • La qualité du README et du démarrage influence-t-elle fortement l’impression globale ?
  • Une application réellement utile mais techniquement classique est-elle désavantagée face à un projet plus expérimental ?
  • Quels profils composent réellement les jurys territoriaux de l’Académie de Nice ?
  • Quels projets ont été éliminés malgré une bonne qualité apparente ?
  • Quelles différences récurrentes apparaissent entre finalistes et projets non retenus ?
10 / Critères

Checklist pour une future idée

  • Le problème peut-il être expliqué en moins d’une minute ?
  • Le projet apporte-t-il une utilité ou une expérience claire ?
  • Existe-t-il un véritable problème algorithmique ?
  • Une partie centrale importante est-elle développée par l’équipe ?
  • Le code reste-t-il compréhensible par les élèves ?
  • Le projet peut-il fonctionner sur une machine avec 4 Go de RAM ?
  • Le projet fonctionne-t-il sans GPU ?
  • Peut-il fonctionner sans connexion Internet permanente ?
  • Peut-il être lancé facilement sur une machine inconnue ?
  • Les dépendances sont-elles limitées et justifiées ?
  • Le jury peut-il tester rapidement un exemple intéressant ?
  • La documentation explique-t-elle les décisions techniques ?
  • Les limites du projet sont-elles reconnues clairement ?
  • L’utilisation éventuelle d’IA est-elle transparente ?
  • Le projet reste-t-il intéressant lorsque l’on retire son interface graphique ?
